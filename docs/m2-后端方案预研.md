## 1. 两条技术路线对比

| 维度 | 路线 A：微信云开发 | 路线 B：FastAPI + MySQL + Redis + APScheduler |
|---|---|---|
| 组成 | 云函数 + 云数据库（文档型）+ 定时触发器 + 订阅消息 | Python 服务 + MySQL 8 + Redis + APScheduler，部署轻量服务器（2C4G 起步） |
| 免运维/成本 | 免服务器、免费额度起步，个人主体免备案域名 | 需服务器、域名与 HTTPS；体验版可勾选"不校验合法域名"绕过备案，公开上线前需备案 |
| 与 M1 数据管道衔接 | 管道是 Python（akshare/pandas），云函数默认 Node，跨环境搬运数据到云库，多一个导入环节 | 同语言同环境，pandas 计算可直接复用 M1 代码，ETL → 计算 → API 一条链 |
| 重计算适配 | 云函数有内存/时长上限（默认 60s），全市场 ~500 ETF × 数千成分股矩阵需拆批或迁出计算 | 无超时限制，多进程/分批可控 |
| 数据模型 | 文档型，多对多（个股×ETF×日期）与序列聚合弱，JOIN 不便 | 关系模型贴合：stock_flow、rank、watchlist、push_log 表天然对齐 |
| 订阅消息 | cloud.openapi.subscribeMessage.send，集成简单 | 服务端直调 subscribeMessage.send，逻辑等同 |
| 可测试/可观测 | 本地调试体验一般 | pytest + 日志/监控成熟 |
| 迁移成本 | 锁定腾讯生态 | 标准栈，易迁移 |

**结论与建议**：M1 数据管道是 Python，M2 的"榜单计算"本质是管道的下游重计算，路线 B 同栈、无超时、关系模型贴合，**建议 M2 以路线 B 为主**（本地/轻量服务器均可起步）；订阅消息两条路线逻辑相同。若 Lead 倾向路线 A，需额外解决"重计算拆分 + 数据导入云库"两个问题（见 §5）。混合方案备选：计算与 API 自建，用户/自选数据放云开发（个人主体体验期不依赖备案）。

## 2. 每日盘后定时任务设计

原则：**任务幂等（带 trade_date 参数可重跑）、步骤可断点续跑、失败有告警**。

```
交易日历校验 → 等待 M1 ETL 当日数据就绪 → 计算服务 → 榜单落库 → 缓存刷新 → 订阅消息推送 → 健康检查/日报
```

1. **触发**：APScheduler cron，交易日 19:30（A 股 15:00 收盘、份额披露多在 17:00–20:00）；交易日历用 akshare `trade_date_hist`，节假日不触发；非交易日补偿任务于次一交易日盘后跑。
2. **数据就绪等待**：轮询 ETL 落库表当日行数 ≥ 前一交易日 80%（阈值 M2 与数据工程师对齐），超时 22:30 告警并标记"数据缺失日"，不影响已有数据服务。
3. **计算服务**（后端与 quant-analyst 接口边界）：读入 Δ份额/净值/权重（M1 产出表），算 Flow(i,t)、5 日/20 日累计、流入强度、ETF 贡献拆解 → 写 `stock_flow_daily`。
4. **榜单落库**：生成全市场/分行业 × 单日/5日/20日 × 流入/流出榜单 → 写 `rank_daily`。
5. **缓存刷新**：见 §3，整批写入新日期 key，原子切换。
6. **订阅消息推送**：见 §4。
7. **重试与告警**：步骤级失败重试 3 次；最终失败记入 `task_log` 并告警（初期告警到日志 + 控制台，后续可接推送）。重跑以 trade_date 幂等覆盖。

## 3. 榜单预计算与缓存策略

数据盘后 T+1、全天不变 → **API 零计算，全部预计算**。

- **预计算表**（MySQL，schema 与数据工程师的落库约定 M2 开工对齐）：
  - `stock_flow_daily(stock_code, trade_date, industry, flow_1d, flow_5d, flow_20d, intensity, top_etfs_json)`：约 2000–3000 只成分股 × 每日 1 行，年增量 < 80 万行，MySQL 无压力。
  - `rank_daily(trade_date, rank_type, period, direction, rank, stock_code, flow)`：榜单每日数千行。
  - 索引：(trade_date, rank_type, period, direction, rank)、(stock_code, trade_date)。
- **Redis 缓存**：
  - 榜单 JSON：`rank:{type}:{period}:{date}`，含 TOP N（建议 100）+ 行业下拉列表，单 key < 100KB，任务完成后整批写入；
  - 个股详情：`stock:{code}:{date}`（序列 + ETF 拆解），预热榜单前 300 名；TTL 72h。
  - **兜底**：Redis 不可用 → API 直查 MySQL 预计算表（走索引），不实时聚合。
- **切换策略**：前端默认取 `latest_date`；每日任务成功后更新 latest 指针（Redis 单 key），无部分刷新，整批替换，失败则保留昨日数据。
- **规模估算**：500 ETF × 数千成分股矩阵，单日计算秒～分钟级，无需分布式。

## 4. 订阅消息提醒接口方案

- **微信能力约束（关键）**：一次性订阅消息=用户每授权一次可推一次；长期订阅模板需特定行业类目资质，个人主体/体验版不可得 → **M2 按一次性订阅设计**，前端在自选/授权页引导重复授权；公开上线获资质后再评估长期订阅。
- **接口设计（路线 B 示例，路线 A 云函数同逻辑）**：
  - `GET/POST /api/watchlist`：自选增删查（按 openid，需 wx.login 换 openid）；
  - `POST /api/subscribe/authorize`：前端 `wx.requestSubscribeMessage` 成功后回传模板 ID + 授权结果，服务端记录授权余量；
  - `POST /api/notify/run`（内部，定时任务第 6 步调用）：查自选股当日 flow，超阈值（如 |flow_5d| ≥ 流通市值 0.05% 或榜单新进 TOP20）→ 逐用户调 `subscribeMessage.send`，记 `push_log`；
  - 失败处理：errcode 43101（用户拒收）删除授权记录，不再重试。
- **防打扰**：每用户每日 ≤ 1 条汇总推送，推送窗口 20:00–21:00；模板字段用 thing/amount 类型，文案含"估算值"口径标注（合规）。

## 5. M2 待确认问题清单（需 Lead/用户拍板）

1. **路线拍板**：路线 A / 路线 B / 混合（自建计算+云开发用户数据）？预研建议 B。
2. **部署形态**：M2 后端跑在本地常驻还是云服务器？决定域名备案动作提前量（公开上线必需 HTTPS+备案域名，个人主体备案对"金融内容"审核敏感，需提前确认）。
3. **微信 AppID 与主体**：M2 联调需真实 AppID；确认个人主体下订阅消息模板可选范围（一次性订阅）。
4. **行业榜单口径**：行业分类用申万一级还是东财行业？行业归属数据由谁提供（数据工程师/后端自采）？
5. **榜单形态**：TOP N 取值；仅流入榜还是流入/流出双榜？
6. **自选与提醒的最小实现**：体验期内测用户少，是否先做"本地缓存自选"版（免登录/openid），提醒再后置？还是 M2 直接上 openid 版？
7. **推送阈值与时间窗默认值**：见 §4 示例，需用户确认默认值。
8. **Schema 对齐**：M1 ETL 落库表结构、字段命名、日期格式需共享数据字典，M2 开工前与 data-engineer/quant-analyst 对齐。
9. **历史回填**：20 日累计需要 ≥20 个交易日历史，M1 期间是否已积累？若不足，M2 需安排回填。
10. **若选路线 A**：重计算拆批方案、云库导入带宽、云函数超时上限如何调整？
